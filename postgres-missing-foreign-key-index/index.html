The mistake

Assuming PostgreSQL indexes foreign keys. It creates an index for PRIMARY KEY and UNIQUE constraints, but not for the referencing column(s) of a FOREIGN KEY.

Why it is dangerous

Without one, every DELETE (or key UPDATE) on the referenced table has to scan the referencing table to check or cascade matching rows, and joins and filters on the column (WHERE user_id = $1, the usual access path) scan it too. It is invisible on small tables and turns into slow deletes, long lock waits and slow pages as the table grows.

How to fix it

Create an index on the referencing column (concurrently, if the table already holds data), or add @@index([userId]) in Prisma:

CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_user_id_idx ON orders (user_id);

A composite index whose first column is the foreign key column also covers it.

FAQ

Does it read schema.prisma?

Yes. Prisma relations without a matching @@index are reported, for PostgreSQL datasources.

Does it connect to my database?

No. The schema is rebuilt by replaying your migrations in order, in memory.

Are my files uploaded anywhere?

No. The checker is Python running inside your browser tab (Pyodide, WebAssembly). Your files are read with the browser's File API and written into an in-memory file system that exists only in this tab. The page makes no network requests except loading the Python runtime and the checker code. There are no analytics. You can disconnect from the internet after the engine has loaded and the scan still works.

Is a clean report a guarantee?

No. It is a static check for known patterns, not a penetration test. A clean report means none of these patterns were found, nothing more.

Can I run the same check on my machine or in CI?

Yes. Every checker on this site is an open-source command-line tool (MIT licence, Python 3.10+ standard library only). The results here are the same as `scan --json` on the command line, except for checks that need git (whether a file is committed or ignored), which cannot run in a browser.
